# NativeRouting 3.0 测试方法

每次构建都应绑定实际 BIN、镜像和源码摘要保存本次结果。测试输出位于 checkout 外，不作为源码交付内容。交付文件的完整性由根目录 `release.json`、`SHA256SUMS` 和 `tools/verify_release.py` 核对。

## 构建与宿主回归

按 [BUILD.md](BUILD.md) 从全新目录构建，运行 `tools/run_host_tests.py`。该入口包含材料摘要及权限、四组页面同步、WG 地址与导出、规则顺序、源地址、多出口、监控、健康恢复、加密 DNS、三语言状态显示和真实 Vue 时间组件。原生校验器、导入器及 Vue 从本次固定输入中提取。

状态显示测试覆盖三语言、零秒、较大秒数、无记录、保护记录数和剩余零秒。翻译替身不自动填入命名占位符，避免掩盖原生翻译器的行为。报告必须注明跳过的检查及原因；缺少依赖不能算作通过。

## 原生固件验证

1. 对新生成镜像的副本运行 BIOS 和 UEFI 启动检查；验证原始交付镜像未被启动或修改。
2. 在隔离虚拟机通过原生接口上传、解析并安装实际 BIN，正常重启，比较保存配置、内核、文件系统及运行覆盖。
3. 打开启动后的完整原生管理页面，核对菜单、样式、活动资源和真实 API 结果。状态秒数应与后台快照对应，无记录应如实显示。截图不得用独立组件夹具替代。
4. 路由或 WG 改动须验证真实接入与出口流量、DNS、断线恢复及错误出口阻断。不得靠删除保护链、清空全部连接或重新应用规则来替代待测的自动恢复行为。
5. 结束时停止测试服务，删除一次性磁盘和临时密钥，确认交付附件摘要未变。

`materials/tests/routing-ui-dom-fixture.py` 是组件回归夹具，使用实际 Vue，但接口响应为模拟数据，样式也不代表原生整页。它适合验证交互和渲染逻辑，不能证明路由器的实际网络状态或原生界面外观。

WG 接口改动还须在一次性副本验证两种保存结果：临时运行目录不可写时，新接口被撤销且恢复写入后可用同一名称重试；本地接口应用成功但后续互访策略失败时，已有接口保留，页面提示检查列表。交叉核对接口列表、数据库、内核网卡和运行快照，使用真实厂商格式的防火墙规则检查停用 `wg1` 后不会影响 `wg10`。不在现场路由器制造故障。

纯 HY2 的整机验收还须分别测试有效和无效凭据、直连局域网服务、关闭 WAN Web 后的管理登录页、已保存的配置升级、域名和端口规则命中及断线阻断。用两台独立设备分别匹配入接口和隧道源地址。

## 验证边界

- iPhone/iPad 网页、视频、息屏及 Wi-Fi/蜂窝切换后的持续出口能力须实机验证；握手、Linux 核心或后台双向字节均不能单独证明。
- CPU、吞吐和多客户端容量须做同条件对照，不从功能回归推导性能结论。
- 加密 DNS、CDN 共享地址、应用缓存和直接 IP 访问存在域名识别边界。
- 应分别覆盖完整规则重应用和稳态恢复，检查 `NR_OUTPUT` 重建期间的迟到 TCP 控制包；控制包与业务载荷应分别记录。
- 双 WAN、DHCP、静态地址、PPPoE 和移动网络恢复应按实际拓扑测试，不能由单一网络场景推断全部可靠性。

## 两种连接方式

原生 WG 手机导出须核对复制的 `.conf` 保留换行、允许地址、Endpoint 和预共享密钥（如已设置）。在手机尺寸的浏览器上对两种原生格式分别测试自动复制和权限拒绝后的全选复制。将标准配置交给 WireGuard 客户端验证握手和流量，将 sing-box JSON 与同一设备的下载内容比较。切换对端或用途后检查旧文本已清除。

1. 在启动后的实际 WG 隧道页面验证新建设备默认原生 WG，可选纯 HY2。验证原生三种用途、标准配置与二维码，纯 HY2 只提供设备经路由器上网。比较扫码、复制与下载的 sing-box 配置。在手机尺寸的浏览器上分别复制完整 JSON 和 HY2 链接，拒绝剪贴板权限后检查手动全选，再切换设备核对内容。用兼容客户端导入分享链接，在相同入口验证正确证书指纹允许连接、改错的指纹拒绝连接。预览原生 WG、纯 HY2 路由器导入包，并尝试重复导入及导入旧包。
2. 用独立客户端通过两种隧道分别发起 TCP、UDP 请求，通过服务端观察的源地址验证出口。多台设备分别建立凭据与端口，核对同时在线的独立会话。单独测试声明网段的原生 WG 互访、来源分流及停用后的方向保护。
3. 核心首次安装和重启后，对照磁盘、临时内存盘、进程来源和可用内存。对照时固定 RAM、固件基线、设备数和网络条件，分别测原生 WG 空载、安装核心及首台纯 HY2 运行三种状态，重复采样。在标准小盘上关机再开机，恢复测试 WAN 后仅从进程和套接字观察监听自行恢复。另测空间不足的内存后备、失败时的磁盘余量以及损坏缓存的恢复。首次启用前分别读取设置、状态及端口占用，检查读取不会创建服务运行目录。
4. 使用 RC16 升级基线时，在 `tools/smoke_upgrade.py` 加 `--check-rc16-transports --rc8-core /absolute/path/to/sing-box-1.14.4-linux-amd64-musl.tar.gz`。使用已登录的原生升级页面接口安装新 BIN。首次可以登录管理页面时就核对双方旧承载记录均已停用，再查原生 WG 对端、已保存纯 HY2 接入身份和旧包拒绝。复查正常启动页面，以及实际运行的内核、覆盖文件及 peer。

从 RC17 验证小盘升级时，给 `tools/smoke_upgrade.py` 传入 `--small-disk-core /absolute/path/to/sing-box-1.14.4-linux-amd64-musl.tar.gz`。夹具在独立的系统盘副本上放入已校验的缓存，保留约 74 MiB 日志空间和 20 MiB 配置空间。先验证 RC17 采用内存盘，再上传本次生成的 BIN，比较手机与路由器导入配置；冷启动后核对两个实际进程的只读挂载和 ELF 摘要，以及原生 WG 对端。

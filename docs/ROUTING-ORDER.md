# 分流顺序与出口策略

新添加的规则显示在列表顶部。同一阶段从上到下匹配，先匹配的有效规则决定出口；编辑或启停规则不改变其位置。

## 匹配顺序

- 域名、端口和协议规则分别按列表顺序执行。源地址和接入接口只是匹配条件，不自动提高优先级；客户端例外规则应放在同阶段的通用规则之前。
- 跨类别依次为显式域名 → 适用的未匹配流量规则 → 端口 → 协议 → 系统默认路由。域名兜底即使显示在列表上方，也在全部显式域名之后执行。
- 普通域名兜底处理剩余适用业务；严格兜底只将大陆公网目标送指定出口，海外或未知目标继续端口和协议规则，最终未匹配才阻断。仅 DNS 方式只影响解析，不固定访问出口。
- 域名、端口、协议和上下行分离列表固定按执行顺序分页显示，不能按线路或源地址临时排序。过滤只改变可见内容，不改变优先级。
- 每条规则可选择多个出口及负载模式。开启线路绑定时断线阻断；未绑定允许按所选策略切换。多线负载的算法与规则先后匹配是不同设置。

规则使用较大 ID 优先的顺序，插入后即可位于顶部。应用设置后应验证新连接；已建立连接和 DNS 缓存按各自生命周期处理。

## 实现与维护

`native_snapshot.lua` 对域名、端口和协议规则按 `id desc` 读取；原生端口/协议链、WG 端口辅助链和上下行分离也采用较大 ID 优先。四个页面的 `show()` 查询固定 `order by id desc`，先排序再分页。

页面源码在 `materials/web-src/routing/`。修改后执行 `python3 tools/sync_routing.py --write`，同步内容哈希、活动 chunk、gzip、manifest 和入口，并保持 WG manifest 元数据一致。

[统一宿主回归](BUILD.md#4-生成镜像并运行宿主回归) 中的 `materials/tests/routing-order-unit.py` 使用真实 SQLite 查询和 Lua 编译器，覆盖重叠源地址、通用规则先匹配、停用例外、ID 间隔、插入顺序、DNS 顺序、跨类别优先级和分页。该测试不操作路由器；原生功能验证要求见 [TESTING.md](TESTING.md)。
